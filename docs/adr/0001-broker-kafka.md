# 0001. Брокер сообщений: Kafka

## Контекст

Сервисы взаимодействуют асинхронно, через брокер (SRS 4.1.2). Требования к брокеру следуют из топиков
SRS 4.1.5:

- строгий глобальный порядок блоков: `chain.blocks` с одной партицией;
- повторное чтение событий (replay), чтобы пересчитать статусы после исправления ошибки или реорганизации;
- последнее значение по ключу: compacted-топики `merchant.events` и `rate.latest`;
- отложенные повторы доставки вебхуков (1 м, 5 м, 30 м) и DLQ;
- холодное хранилище в ClickHouse без Kafka Connect.

Стенд — одна машина. Рабочим узлам выделено 22,5 ГБ, и постоянная нагрузка занимает их целиком (SRS 6.2).

## Решение

Kafka, развёртывание — Strimzi в режиме KRaft: 3 брокера, RF = 3, `min.insync.replicas = 2`, heap 768 МБ,
около 3,5 ГБ на кластер (SRS 4.1.5, 6.2). Топики, ключи и число партиций — по таблице SRS 4.1.5. Доставка
at-least-once, все потребители идемпотентны. Отложенные повторы вебхуков — цепочка топиков
`webhook.retry.1m`, `.5m`, `.30m` и `webhook.dlq`.

## Рассмотренные варианты

Сравнение — SRS Приложение Б.1.

| Критерий | Kafka | RabbitMQ | NATS JetStream |
|---|---|---|---|
| Модель | Распределённый лог | Очереди и exchange (+ Streams) | Pub/sub + персистентные стримы |
| Replay | Нативно | Только Streams | Есть |
| Порядок | В партиции по ключу | В очереди | В стриме или subject |
| Compacted-топики | Есть | Нет | Есть (KV поверх стримов) |
| Отложенные повторы | Через retry-топики (вручную) | Нативно (TTL + DLX, delayed exchange) | Через `NakWithDelay` |
| Интеграция с аналитикой | Движок Kafka в ClickHouse, Connect, Debezium | Слабее | Слабее |
| Ресурсы | Высокие (JVM) | Средние | Минимальные |
| Оператор K8s | Strimzi | RabbitMQ Cluster Operator | NACK / Helm |

Почему Kafka:

1. Блокчейн по своей природе упорядоченный лог. Топик `chain.blocks` с одной партицией повторяет эту модель
   напрямую.
2. Replay позволяет пересчитать статусы после исправления ошибки или реорганизации.
3. Compacted-топик `rate.latest` восстанавливает кэш курсов после рестарта.
4. ClickHouse читает топики напрямую — холодное хранилище без дополнительных сервисов.
5. Зрелый Strimzi и метрики для нагрузочного теста и дашбордов (SRS 8.1, 8.3).

Что подошло бы лучше. При нагрузке стенда (сотни RPS, блок раз в 2 секунды) NATS JetStream покрыл бы все
потребности (порядок, replay, KV для курсов, отложенные повторы) при кратно меньших ресурсах. Для доставки
вебхуков с повторами по расписанию естественнее RabbitMQ. Kafka оправдана при масштабировании на несколько
сетей и тысячи событий в секунду, а также при росте числа независимых потребителей событий (аналитика,
бухгалтерия, AML).

## Последствия

- Kafka — самый тяжёлый из трёх вариантов: около 3,5 ГБ из 22,5 ГБ рабочих узлов.
- Отложенные повторы вебхуков строятся вручную: `webhook-service` ведёт цепочку retry-топиков и DLQ.
- Доставка at-least-once: все потребители дедуплицируют события по `event.id`, переводы — по
  `blockHash + txHash + logIndex` (SRS 4.1.5).
- Порядок между `chain.blocks` и `chain.transfers` не гарантирован: `invoice-service` ведёт каноническую
  цепочку по `chain.blocks` и применяет перевод, только когда его блок в неё входит.
- Холодное хранилище — движок Kafka и materialized view в ClickHouse, без Kafka Connect. Витрины
  ClickHouse пересобираются из топиков в пределах их retention (SRS 4.1.6).
- Strimzi и CR Kafka генерирует Ansible-роль в GitOps-репозиторий (SRS INF-2.3, ADR 0004).
