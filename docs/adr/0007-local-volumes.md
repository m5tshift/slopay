# 0007. Механизм локальных томов

## Контекст

Постоянные тома нужны Kafka, базам данных, наблюдаемости, Zot и S3 (SRS INF-1.3), а также Anvil: состояние
цепочки сохраняется на PV (SRS раздел 5). У каждого из трёх рабочих узлов есть отдельный диск под данные
на 50 ГБ (SRS 6.1).

## Решение

Local PV на отдельном диске рабочих узлов через local-path-provisioner; диск подключается через
конфигурацию Talos (SRS INF-1.3). Под с данными привязан к своему узлу. Отказоустойчивость обеспечивает
репликация самих компонентов; SRS задаёт её для хранилищ данных:

| Компонент | Репликация |
|---|---|
| Kafka | RF = 3, `min.insync.replicas = 2` |
| PostgreSQL | 2 инстанса |
| MongoDB | replica set из 3 узлов |
| ClickHouse | 1 инстанс, витрины восстанавливаются из Kafka |
| Valkey | 1 инстанс (кэш) |

Бэкапы PostgreSQL и MongoDB хранятся в S3 7 дней (SRS 4.1.6).

Для наблюдаемости (VictoriaMetrics, VictoriaLogs, Tempo), Zot, S3 (Garage) и Anvil SRS репликацию не задаёт.

## Рассмотренные варианты

SRS альтернатив не сравнивает: решение опирается на то, что каждое хранилище данных само реплицирует данные
или восстанавливает их из другого источника.

## Последствия

- Под с данными не переезжает на другой узел: при отказе узла его тома недоступны, пока узел не вернётся.
  Работу продолжают реплики на других узлах. Вывод из INF-1.3: реплики одного компонента должны стоять
  на разных узлах.
- ClickHouse и Valkey работают в одном экземпляре. Витрины ClickHouse пересобираются из топиков Kafka
  в пределах их retention (7 дней); потеря данных Valkey не нарушает корректность (SRS 4.1.6, 4.1.7).
- Компоненты без репликации в SRS (наблюдаемость, Zot, S3, Anvil) при отказе узла теряют доступ к своим
  данным до его возвращения.
- Объём данных ограничен диском узла (50 ГБ).
